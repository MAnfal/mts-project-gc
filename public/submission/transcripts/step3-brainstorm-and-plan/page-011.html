# SOPs — Decision Tree

when; SOPs say how; bibles say what good looks like. They are procedures, not suggestions.

**Looking for a standard rather than a procedure?** That's the bibles —
`.claude/resources/bibles/README.md`. An SOP is a sequence you run once at a known moment
("before planning a rename, do these four greps"); a bible page is a rule that holds
whenever you're in its territory ("an orchestrator contains no domain logic"). If you want

# Verification Gates

Every change runs these before it is delivered — the implementer as a self-check, the lead
as an audit. Run in order; all must pass. On failure, fix and re-run.

## The standard set

Read the command table in `.claude/resources/project.md`. Skip anything marked `N/A`.

1. Type check
2. Lint
3. Unit tests
4. Build
5. Chunk-specific assertions from the chunk's plan

**Run the type check last.** Test runners transpile without type-checking and will pass
errors a type checker catches, so a tests-first ordering masks real failures.

**Re-run after the last edit.** A clean result from before the final change is stale. This
is the single most common source of a CI failure on work that was reported green.

## Capture a baseline first

Before running anything that emits errors or warnings, capture the pre-existing state on
the base branch — before the chunk's changes. Then grade the **delta**, never the absolute
count. Without a baseline, pre-existing failures get attributed to the chunk, and agents
burn iterations trying to zero out noise they didn't create.

```bash
BASELINE_DIR=$(mktemp -d "/tmp/baseline-XXXXXX")
<type check command>  2>&1 | tee "$BASELINE_DIR/types.txt"
<lint command>        2>&1 | tee "$BASELINE_DIR/lint.txt"
<test command>        2>&1 | tee "$BASELINE_DIR/tests.txt"
echo "BASELINE_DIR=$BASELINE_DIR"
```

Record the counts and the directory path in the PR body so the reviewer can find them.

## A gate is untested code until it has been seen red

A gate is the only code in a change that nobody exercises: it runs once, prints nothing,
and is believed. Break the thing it protects and watch it fail before trusting it.

The full negative-control cycle is **four** steps, not two:

1. Plant the canary
2. Confirm the gate fires
3. Remove the canary
4. **Confirm the gate returns clean**

Step 4 is what catches a failed revert — wrong path, partial edit, untracked file — which
otherwise leaves the gate stuck in the canary state reporting a manufactured clean.

Run the control **per assertion**. A gate with five needles needs five probes; proving one
needle real says nothing about the other four.

## Prove the gate can fail on the base tree

Run each gate against the tree **before** the chunk's work and assert it exits non-zero.

```bash
if <the gate command>; then
  echo "GATE CANNOT FAIL — it already passes on the base tree" >&2
  exit 1
fi
```

Printing the return code for a human to read is the same defect this rule exists to catch:
a check whose result has to be interpreted reports success either way.

What counts as failure evidence depends on the gate — don't demand a needle from a gate
that has none:

| Gate kind | Evidence to record |
| --- | --- |
| Content gate (grep) | the needle, the file it targets, and why base failed — **absence** for a gate proving content was added, **presence** for one proving it was removed |
| Test | the failing test name and its assertion |
| Type check / lint | the diagnostic code and the file it fired on |
| Build / script | the non-zero exit status and the error line |

Three shapes to watch for:

- **A failure that is not about the chunk.** A non-zero exit on base proves the gate *can*
  fail; it does not prove it fails **because the work is missing**. Run the gate on base
  and on the finished tree and compare the **error text**, not the exit status. Identical
  output both times means the command is broken, not the tree — the gate is vacuous in the
  direction the exit code cannot show. Most common cause: a malformed invocation the tool
  rejects before it ever reaches the project (`pnpm test --run` exits non-zero with
  `ERROR Unknown option: 'run'` on any tree, with or without a `package.json`).
- **An OR pattern whose second alternative already matches.** `grep -E 'a|b'` returning
  hits proves nothing about *which* one matched. Verify each needle separately; if one
  branch matches the base tree, the gate is permanently vacuous.
- **An empty corpus.** `git diff --name-only` sees tracked files only, so a gate auditing
  new files passes against an empty stream. Union it with
  `git ls-files --others --exclude-standard`.

## Shapes that silently pass

**A negated quiet grep is never a gate.** `grep -qv PATTERN` asks "is there at least one
line that does NOT match" — true of almost any non-empty input. Count and assert instead:

```bash
hits=$(grep -cE '<pattern>' "$file" || true)
[ "$hits" -ge 1 ] || { echo "FAIL: <what is missing>" >&2; exit 1; }
```

**`grep -q X && echo OK` fails open under `set -e`.** Bash exempts the left operand of
`&&`, so a failing grep prints nothing and execution continues — the gate reports pass
while its check never ran. Use an explicit `if`:

```bash
if grep -qr "symbol" src/; then echo OK; else echo "FAIL: symbol absent" >&2; exit 1; fi
```

# Regulatory Monitoring — Demo Build

## Problem Statement

The regulatory-monitoring workflow is proven only as a throwaway POC on the `poc` branch:
a Next.js app with dev-only pages that writes to local disk and can't be deployed. The
take-home review needs a deployed Vercel app that shows two things. A GC can run a live
weekly triage and get back a verified, owner-routed report. A reviewer can follow the eval
story (context → iterations → results → learnings) and drill down to any run's trace. The
POC's recorded evals, which cost ~$125 to produce, carry over unchanged as the evidence.

## User Stories

### US1 — GC runs a live weekly triage `[P1]`

**As** the General Counsel of a mid-size company, **I want** to pick my company profile
and a week, then watch the monitor work and get back only the federal rules that affect
us, each with a priority, deadline, owner and source, **so that** I can triage in ten
minutes and forward items without re-checking them.

**Acceptance Criteria:**

- Given the new-run screen, When I pick the Ledgerly preset and the week Nov 2–6 2026 and
  press Run, Then I see each pipeline step stream in under a plain-English name (no
  internal model name), with counts and timings, and the report appears when the run
  finishes.
- Given a finished run, When I read the report, Then every item shows a priority assigned
  by code, a deadline verified against the Federal Register (or none), an owner from the
  profile's areas, and a link to the official record.
- Given a step that fails 3 times in a row, When the run stops, Then the failed step shows
  a timeout message and a Retry button that reruns with the same settings, and the failed
  run is still listed after a page reload.
- Given I edit a preset's profile or owners, When I run, Then the run uses my edited
  profile, and the preset's file on the server is unchanged.
- Given a run in which nothing applies, or an item fails verification, When the report
  renders, Then it says "nothing affects you" with the closest calls, or lists the
  held-back item separately instead of in the report.

**Independently testable because:** with no eval screens and no chat, a GC can still run a
live triage end to end on the deployed URL.

### US2 — Reviewer follows the eval story `[P1]`

**As** an interviewer reviewing the take-home, **I want** a summary that states the
verdict and the CARL story first, then drill-down to iterations, cases, model comparison
and raw traces on demand, **so that** I can judge the eval work in minutes without being
overwhelmed.

**Acceptance Criteria:**

- Given the eval summary, When it loads, Then the headline verdict, the CARL rows, the
  scoreboard (target / live, all weeks / held-out / baseline) and the iteration chart all
  come from the recorded data, and each number names its split and run count.
- Given an iteration, When I open it, Then I see its hypothesis, change, result against the
  setup it replaced, what moved, and the decision.
- Given the cases view, When I select a case and a run, Then I see the filter's reason, the
  trace-check result and the judge verdicts, and I can open that run's full trace.
- Given the models page, When it loads, Then it compares every model the arena ran on the
  same measures and states why the live model was chosen.
- Given any recorded suite, When I look for its runs and traces, Then all 9 suites, the 22
  example runs and iterations 00–07 are present. No recorded result is dropped.

**Independently testable because:** with no live pipeline at all, the eval screens are
fully static and demo the evaluation work on their own.

### US3 — GC asks follow-up questions about a report `[P2]`

**As** the GC, **I want** to ask questions about a finished report ("summarize for the
CEO", "did anything on crypto come close?"), **so that** I can reuse the result without
rerunning anything.

**Acceptance Criteria:**

- Given a finished report, When I ask a question, Then the answer streams in and uses only
  the report, its sources and the run's screened-out list.
- Given no finished report, When the screen renders, Then the chat box is hidden.

**Independently testable because:** it needs only US1's finished-report state, which a
recorded example run already provides.

1. **Plain Vercel AI SDK + AI Gateway, not Flue/Pi** (user, 2026-11-22). The POC pipeline

   deploys `main`, and the user verifies each chunk on the deployed URL as it lands. A
   long-lived plan branch would delay that by the length of the plan.
3. **The POC's decision path is ported byte-identical** (chunk 02, verified by gate). The
   recorded eval numbers describe the POC's pipeline. They describe the demo only if the
   demo runs the same pipeline. "Decision path" means: `prompts.yaml`, `prompt-sets/`,

   final config hashes to `9a0f857741`; the only difference is `userView.setup` being
   promoted to the 06 setup (commit `2f91080`).
4. **Browser-only persistence (IndexedDB)** (user, 2026-11-22). Vercel functions can't write
   durable files, and `sessionStorage` or memory loses runs on refresh. Server-side traces
   of live runs are not kept. The write-up states this limitation; the recorded suites keep
   full traces.
5. **No spend guard in code** (user, 2026-11-22). The demo relies on the ~$20 Gateway
   balance. Risk: anyone with the URL can spend it. The user accepts this for a demo
   shared only with interviewers. The POC's file-based spend ledger (`store.ts`) is not
   ported.
6. **All recorded evals ship as static files via Git deploy** (user, 2026-11-22). Measured:
   traces ~82 MB (already gzipped), run records ~13 MB gzipped, example runs ~2 MB,
   iterations 1.3 MB; ~900 files. Vercel's 100 MB cap applies to CLI uploads, not Git
   builds; the file cap is 15,000 ([Vercel limits](https://vercel.com/docs/limits)). The
   bundle is built from the tracked `poc/data/evals` (all 9 suites) and
   `poc/data/user-view`, **not** from the gitignored `poc/data/exports`, which covers only
   2 suites. Fallback if the deploy fails on size: traces only to Vercel Blob or R2.
7. **Function duration** — Vercel Hobby Fluid compute allows 300 s, both default and maximum
   ([Functions limits](https://vercel.com/docs/functions/limitations)). The POC measured
   65 s typical and 87 s worst case for the live setup. The streaming route sets
   `maxDuration = 300`. Chunk 01's probe proves it on the deployed URL before the design
   depends on it.
8. **Retry: 3 attempts per failing step, back-off 2 s → 4 s → 8 s** (user rule: "up to 3"
   attempts; the back-off values are ours). The longest added wait is 14 s, which keeps
   the 87 s worst case well inside 300 s. After the third failure the run fails with the
   step's timeout message and a Retry that reuses the saved settings. Retries never change
   a decision; they only re-issue the same request.
9. **Public step names map from internal stage IDs in one table** (chunk 03). The GC never
   sees internal model or component names. A gate greps the GC-facing bundle and responses
   for the internal names.
10. **Eval numbers are computed from data, never typed from the mockups.** The hi-fi copy
    in `design/` is layout and tone, not the spec for numbers. In particular, the mockup
    shows the baseline as 63/69 in the scoreboard but 71/81 at chart point 00. Those come

# Migration Verification — Parity Testing

**Scope: code ports, not database migrations.** This page covers porting a runtime, executor or pipeline to a new contract shape and proving the behavior is unchanged. Verifying a **database** migration — replaying the Flyway SQL against a throwaway database — is a different procedure and is out of scope for this page.

The standard verification pattern for port-style migrations: a golden-fixture baseline + side-by-side executor parity tests that make "identical behavior minus the refactored axis" a provable claim.

## Two-gate structure

A migration plan should declare both gates up front:

1. **Golden-fixture baseline** (harness chunk, before migration starts): capture the CURRENT engine's verdicts against a known fixture set BEFORE any new code lands. This baseline is the ground truth.
2. **Side-by-side executor parity** (per-migration chunk): for each ported executor, assert that OLD and NEW produce identical output on the same inputs. The parity test runs both and diffs.

## Why it works

The golden-fixture baseline makes the cutover a mechanical diff: if zero parity-harness lines change and zero intentional behavior changes appear in the diff, the migration is provably identical. Without the baseline, "identical behavior" is a trust-based claim.

## The cutover chunk

The final entry-point flip becomes a verdict-diff against the baseline. Expected: zero changes. Any change is either an intentional behavior difference (document it) or a bug.

## Applies when

- A runtime or executor is being ported to a new contract shape
- A pipeline is restructured with the same I/O behavior
- A refactor claims "identical behavior" — use this pattern to prove it

## Pair with migration oracle

When the migration also involves a contract-shape change (old fields → new fields), pair with the transitional adapter pattern. See @patterns/migration-oracle.md.

## Evidence

An SEO-engine pipeline migration paired a golden-fixture parity harness (landed BEFORE any new code) with side-by-side executor parity tests, then flipped the entry-point in a dedicated cutover chunk. The cutover diff itself was zero-parity-change; 14 legacy files (-1904 lines) were deleted in the same commit. The combination turned a high-risk cutover into a verifiable diff.

# Chunk 03 — Port the pipeline with public step events and retries

## Context

Chunk 02 ported config and the deterministic libraries. This chunk ports the pipeline
itself from `poc:poc/src/lib/pipeline/` (`context.ts`, `stages.ts`, `run.ts`,
`excerpts.ts`), plus the model layer from `poc:poc/src/lib/gateway.ts` and `models.ts`.
It ports only the live setup `jev-sonnet-strict-passages`; the baseline and arena paths
stay on `poc`. The sequence is:

1. scan
2. Jev relevance scores
3. Jev-picked passages for the top 20
4. strict LLM filter
5. re-fetch and verify dates
6. tier and route (code)
7. write actions (LLM)

Three changes, none of which may alter a decision:

1. **Public step events instead of server-side files.**
   - The POC's `RunCtx` writes run JSON and a JSONL trace to disk (`store.ts`,
     `trace.ts`). Here it instead emits typed events to a callback, which chunk 04 streams
     to the browser.
   - A **single table** maps each internal stage ID to a GC-facing label, e.g.
     `filter:jev` → "Ranked them by relevance to <company>".
   - **No event payload may contain** an internal model or component name: no "Jev", no
     `typesafe-ai/jev`, no model IDs, no prompt text.
   - The spend ledger (`store.ts` `spentUsd`/`budgetUsd`) is **not** ported (no spend
     guard, by user decision).
2. **Retries.** Every external call is retried up to 3 attempts with back-off of 2 s, then
   4 s, then 8 s. External calls are Federal Register/govinfo fetches, LLM calls and Jev
   calls. The longest added wait is 14 s; the POC's 87 s worst case plus 14 s stays far
   inside Vercel's 300 s limit. After the third failure, the run emits `step.failed` with
   a plain-English timeout message and ends with `run.failed`. A retry re-issues the same
   request and never changes its inputs.
3. **The reason-text leak is fixed.** The POC's `stages.ts` (around line 281) falls back to
   `` `Jev p=${…} (no LLM reason)` `` for an item's reason. Replace it with a neutral
   fallback: "Flagged as relevant to your profile". The internal probability may still go
   to the server log, but never into the item.

**Parity is the contract.** This is a port, so prove it is identical on a recorded run.
Copy one recorded `jev-sonnet-strict-passages` trace from the suite
`poc:poc/data/evals/arena-2026-11-21-23-16-du8/traces/`; pick one whose run finished with

- Run the ported pipeline on the same frozen week.
- Assert that the filter decisions, `tier.assign`, `owner.assign` and the final items equal
  the trace's, **ignoring only the `reason` text the leak fix changed**.

# Chunk 04 — Streaming run, Running and Report screens, IndexedDB history and Retry

## Context

Chunk 03 gives `runPipeline(config, emit)`, which emits public `RunEvent`s
(`src/lib/pipeline/events.ts`). This chunk makes it a product. A route streams those
events to the browser. The browser renders the **Running** screen
(`design/HiRunning.dc.html`) and then the **Report** screen (`design/HiReport.dc.html`),
and saves every run — config, events, result, status — in **IndexedDB**. The server keeps
nothing (user decision: browser-only persistence).

User rule for failures: after 3 failed attempts on a step (03 already retries), the run
fails. The failed step shows the timeout message right under it, with a **Retry** button
that reruns with the same saved settings. The failed run is saved, so it shows again after
a reload.

There is no new-run form yet (chunk 05 builds it). To make the slice usable now, `/`
shows one button: "Run Ledgerly · Nov 2–6". It starts a run with the `ledgerly` preset
and the frozen week `2026-11-02`–`2026-11-06`.

## Acceptance Criteria

- Given `POST /api/run` with `{profileId:"ledgerly", windowStart:"2026-11-02",
  windowEnd:"2026-11-06"}`, When it runs, Then the response is `application/x-ndjson`
  with one `RunEvent` per line, ending in `run.done` or `run.failed`. The route declares
  `maxDuration = 300`.
- Given a body that fails validation, Then the route returns 400 with a plain message and
  starts no run. Validation failures: an unknown `profileId`, a window longer than
  `config/app.yaml` `maxWindowDays`, `windowEnd < windowStart`, or a custom profile
  missing `summary`.
- Given a custom profile in the body, When it runs, Then the pipeline uses it. The server
  never writes it anywhere.
- Given the Running screen, When events arrive, Then:
  - steps render as done, in progress or waiting, with counts and timings;
  - the step in progress shows its sub-items, with a spinner that respects
    `prefers-reduced-motion`;
  - the status line is an `aria-live="polite"` region;
  - skeleton placeholders hold the report's space.
- Given `run.done`, Then the Report renders:
  - "Worked for Ns" (collapsible back to the steps);
  - a heading and summary written from the items, e.g. "3 sanctions notices for Marcus,
    nothing Critical", built from counts, tiers and owners in code, no LLM;
  - tier counts as paired status badges, plus a "Held back N" badge;
  - a table: Priority | Rule and what to do (with numbered source chips) | Deadline with
    "Verified" | Owner;
  - "Why <tier>?" for each item, built from the tier rule's reason;
  - "Draft email to <owner>", a `mailto:` with a plain-text body built from that owner's
    items;
  - "N not relevant · see why", listing the screened-out documents' one-line reasons;
  - Download `.md` (the pipeline's markdown) and `.json`;
  - the Sources | Profile right panel.
- Given `run.failed`, Then the failed step shows its timeout message under it and a
  **Retry** button. Retry starts a new run with the identical saved config.
- Given a reload at any point after a run finished or failed, Then the sidebar's "Recent
  runs" lists it from IndexedDB and opening it re-renders it from the stored events, with
  no network call.
- Given a reload during a run, Then that run shows as "Interrupted" with Retry. A stream
  can't resume after a reload; say so in the UI.

# Chunk 06 — Edge states, held-back items, and example runs

## Context

Chunks 04–05 render the happy path. This chunk adds the states in
`design/HiStates.dc.html`, plus the "Examples" list in the GC sidebar:

1. **Nothing applies.** A run with 0 items shows "Nothing affects <company> this week":
   - "All N federal documents from <week> were checked against your profile";
   - **Closest calls**: the first 3 of `run.done.screenedOut`, as title · reason, from
     chunk 03;
   - a "Download 'no action' memo" button, which produces a markdown memo built in code.
2. **Held back.** `run.done.dropped` lists items that looked relevant but failed
   verification, e.g. a date not found in the published text. They show **above** the
   report table in the orange status style:
   - each has "Open on Federal Register" and "Add after checking";
   - "Add after checking" moves the item into the table with a "Confirmed by you" badge,
     stored on the run in IndexedDB;
   - held-back items never enter the table on their own: that would violate Principle 3,
     that every surfaced date is verified. A person confirming it is the documented
     exception, and the badge makes it visible;
   - the downloaded memo lists held-back items in their own section.
3. **Failed run, refined.** Steps that finished stay visible. The failed step shows the
   red icon, its message, and "Retry" plus "Edit settings". Chunk 04 shipped the
   mechanics; this chunk matches the hi-fi copy and layout.
4. **Examples in the sidebar.** Chunk 07 publishes the POC's 22 example runs under
   `public/evals/user-view/`. List the ones with status `done` under "Examples" in

# Chunk 11 — Follow-up chat on a finished report

## Context

Once a run finishes, the GC can ask about the result: "Summarize for the CEO in 3 lines",
"Did anything on crypto come close?". The composer and suggestion chips sit at the bottom
of the Report, as in `design/HiReport.dc.html`, the same pattern as GC AI's follow-up box.
**Until the run finishes, the chat is hidden.**

Grounding rule: answers use **only** this run's report. That means:

- the items, each with tier, deadline, owner, reason, action and citation;
- the sources (titles, FR citations, links);
- the held-back list;
- `screenedOut`: titles and one-line reasons of the rejected documents;
- the profile the run used.

No web search and no other runs. When the answer isn't in that material, the model says
so. The chat is stateless on the server. The browser sends the run context plus the
conversation, and the turns are saved on the run's IndexedDB record, so they come back
after a reload.

Chunk 04's `ReportView` takes a `followUp?: ReactNode` prop. This chunk mounts the chat
through that prop from `src/app/runs/[id]/page.tsx` and `src/app/examples/[id]/page.tsx`,
the latter created by chunk 06. It does **not** edit `ReportView.tsx`.

The model and system prompt come from config: add `followUp: {model, system,
suggestions[]}` to `config/app.yaml`. Never add them to a decision-path file (`prompts.yaml`
or `experiment.yaml`).

The GC-facing rule still applies:
- Answers must not reveal internal names.
- The context sent to the model is built by a function that copies only public fields, so
  internal names never enter it. Run `assertPublic` (chunk 03) on the context object.

## Acceptance Criteria

- Given a finished or example run, Then the suggestion chips and composer render under the

- Given a running, failed or interrupted run, Then no chat UI renders.

- Given the request body, Then the route rejects (400):

<context>
Reads a chunk's `plan.md`, works out which files it touches, matches those against the
convention map in `.claude/resources/project.md`, and writes a complete `rubric.md`.

This exists so review checks are **systematic rather than remembered**. A hand-written
rubric only contains what the planner happened to think of that turn; a generated one
contains whatever the project has declared about the kind of files in the chunk.
</context>

<usage>

## Step 1 — Read the chunk

From `$ARGUMENTS/plan.md`, extract:

- The chunk title from the `# Chunk NN — <Title>` heading

- The acceptance criteria

## Step 2 — Match the convention map

Read the **Convention Map** in `.claude/resources/project.md`. For each file path, find
every row whose glob matches. Deduplicate: two files hitting the same row produce one
rubric item.

Each matched row contributes:

- Its **review checks**, as rubric items
- Its **doc** reference, so the reviewer reads the rule rather than inferring it

**The `Doc` column points into `.claude/resources/bibles/`.** Carry the path onto the
rubric item itself, so the reviewer opens the rule instead of grading from memory:

```
- [ ] Interface-first: the contract is its own module and the class implements it
      explicitly — `.claude/resources/bibles/swe/patterns/service-design.md`
```

Cite the **leaf page**, never a bible's `decision-tree.md`. A reviewer handed a routing
table has to go find the rule, and a reviewer who has to go find the rule grades on memory
instead.

If a row's `Doc` is `—`, emit the review check without a citation rather than inventing a
page. If the map is empty or nothing matches, say so in your report rather than silently
producing a thin rubric — an empty map is a project that hasn't declared its conventions
yet, and that is worth knowing.

### When the chunk touches `.claude/` itself

Any chunk editing a prompt, skill, command, template, or bible is governed by the
prompt-engineering bible even when the Convention Map has no row for it. Follow
`.claude/resources/bibles/prompt-engineering/decision-tree.md` to the leaf pages that apply
— frontmatter, sizing, XML structure, taxonomy — and emit them as chunk-specific checks.
This is the one case where you add citations the map didn't supply.

## Step 3 — Derive test expectations

For each file gaining **new behavior** (not a re-export, not a moved line), emit a specific
test item naming the file and the functions:

```
- [ ] Unit tests for `parseConfig()` and `validateConfig()` in `config.spec.ts`
```

Use the project's test-file convention from the Convention Map. One item per file that
gains testable behavior — not one per layer, and not a generic "has tests".

If the chunk adds no testable behavior, write `N/A — <which of types / declarative config /
docs this chunk is>`. An explicit N/A is a grade; a blank is an omission.

**Always emit the constructed-input item** for any chunk with testable behavior, verbatim:

```
- [ ] For each defensive branch in this chunk — a guard, a boundary, a clamp, a
      uniqueness or normalization check — a test exists whose input cannot come from the
      committed fixture. Delete the branch and confirm a named test goes red
```

This one is standing rather than derived. A test drawn from real captured output only ever
contains the cases its source produced, so the guard for the case it didn't produce is
pinned by nothing and deletes green while the suite stays whole. It is the single most
common surviving mutant, and it is invisible to every other item in the rubric.

the idealized criterion fails correct work. Resolve toward the plan's constraint and note
