  • (1) Grader types: Code-based graders are "Fast", "Cheap", "Objective", "Reproducible", but "Brittle to valid variations". Model-based graders are "Flexible" and "Captures nuance", but "Non-deterministic" and "Requires calibration with human graders". Human graders are the "Gold standard quality" but "Expensive" and "Slow". Advice: "deterministic graders where possible, LLM graders where necessary".

  • (2) Outcomes vs transcripts: An outcome is the final environment state (e.g., a reservation exists in the database), not the agent's claim. Advice: "grade what the agent produced, not the path it took". Add transcript-based checks (tool use, code quality) on top of outcome checks.

  • (3) Capability vs regression: Capability evals ask "What can this agent do well?" and start at a low pass rate. Regression evals ask "Does the agent still handle all the tasks it used to?" and should sit near 100%. Mature capability evals can "graduate" into regression suites.

  • (4) pass@k vs pass^k: pass@k is the chance of at least one success in k attempts; use it where "one success matters". pass^k is the chance all k trials succeed; use it for "customer-facing agents" where consistency is essential. Example: 75% per-trial over 3 trials gives (0.75)^3 ≈ 42%.

  • (5) Dataset/task construction: "20-50 simple tasks drawn from real failures is a great start." Source from manual checks, bug trackers, and support queues. Tasks must be unambiguous: "two domain experts would independently reach the same pass/fail verdict." Write a reference solution per task; a "0% pass rate across many trials" usually signals a broken task. Balance cases where a behavior "should occur" and where it "shouldn't"; avoid "class-imbalanced" evals.

  • (6) Transcripts, saturation, isolation, partial credit: "Read the transcripts" to confirm failures are fair. A 100% eval "provides no signal for improvement", so revise saturated or unfair evals. Start each trial from "a clean environment" to avoid correlated failures and inflated scores. "build in partial credit" for multi-component tasks. Make graders resistant to hacks.

  • (7) LLM judges: Calibrate "closely with human experts". Let the judge "return 'Unknown'" when information is insufficient. Use "clear, structured rubrics" and grade each dimension with "an isolated LLM-as-judge". Human review is needed "only occasionally" once the judge is robust. Other methods listed: pairwise comparison, reference-based evaluation, multi-judge consensus.
