Two separate things are going on.

Why the trace is big: it's mostly repetition in the log, not in the work. Each Jev call is sent the company profile (~1.5 KB) plus one document (~1 KB), and we call it once per document, ~450 times a week. The trace stores every input verbatim, so the same profile text appears 450 times, about 1 MB per run. The fix is simple and loses nothing: store the profile once in run.start, and have each jev.call keep just the document plus a pointer to it. The exact input can still be rebuilt byte for byte, and traces shrink about 60%, or about 20× once gzipped.

Are we brute-forcing? For this data, deliberately, and it's cheap: ~450 docs a week × ~700 tokens is about $0.013 per week on Jev. That's Jev's job: a cheap, high-recall first pass so the expensive LLM only sees ~30 survivors. Your concern is right at bigger scale, though (the interviewer's "5M tokens of search results"). The answer there is a funnel where each step is cheaper per item and sees fewer items:

  everything ──► ① free rules (agency, CFR part, doc type from the profile) ──► ② Jev on title+abstract
