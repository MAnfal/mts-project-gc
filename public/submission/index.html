Reg Monitor

A weekly triage of federal rules for the general counsel of a mid-size company. Pick a company and a week; get back only the rules that affect it, each as one action item with a tier, deadline, owner and source link. Every date and citation is checked against the Federal Register, and any deadline under 90 days is Critical.

The prototype

Two surfaces for two audiences, behind one landing page.

Run the monitor GC app Pick a company profile and a week, watch the run stream step by step, and read the report: one action item per rule that matters, plus a follow-up chat grounded in that report. Recorded example runs in the sidebar replay without an API key. Eval results Reviewers The verdict and headline numbers against a single-prompt baseline first, then drill down: the iteration log, every case, model comparisons, raw traces, and the live setup with its prompts in full.

Design

Designed before any product code, in three passes on one canvas: lo-fi to agree on the screens, mid-fi to settle the flows, and hi-fi in GC AI’s own visual language.

Lo-fi, mid-fi and hi-fi screens HTML The new-run screen, the live run, the report and the eval drill-down at each fidelity. The hi-fi row is what the build was checked against. A large self-contained file, so it takes a moment to open.

Execution

Four Claude Code sessions, in the order they ran. Each is a complete transcript: the prompts, the model’s reasoning, the tool calls, and the reviews that sent work back. The build runs on the loop described in Primitives of spec-driven development.

  1. 1
    Proof of concept & eval harness Nov 21

    From the RFC to a working pipeline and a way to judge it. Settled the harness (plain AI SDK through the AI Gateway), built frozen eval weeks with hand-checked answer keys for three companies, pitted four vendors’ models against a single-prompt baseline, moved every prompt, model and threshold into YAML, and recorded the first iterations with their diffs.

    Read transcript →
  2. 2
    Eval iterations Nov 21

    Improving the system under a fixed budget, one change at a time. Every change had to be chosen from error analysis on the tuning weeks and hold up on held-out weeks. A majority vote and an exclusion prompt were rejected; reading the best passages of each rule’s full text found the rule every earlier run missed, and went live.

    Read transcript →
  3. 3
    Brainstorm, design & plan Nov 22

    Turning the POC into a demo. Decided what the GC sees (generic progress, never internal model names), where runs live (the browser’s IndexedDB, not a server), and how the evals read (verdict first, drill-down on demand). Designed the screens at three fidelities, then wrote the spec and an 11-chunk plan.

    Read transcript →
  4. 4
    Build Nov 22–23

    The plan executed end to end. Each chunk went to an implementer agent and was graded by a fresh reviewer against its rubric, then merged through its own pull request. The pipeline’s decision path was ported byte-identical to the POC and checked by a parity gate, so the recorded evals still describe what runs.
